## PATCH V2: петли, зеркальный блок, профили и фрамуга

Production-файлы остаются прежними, новых assets и V3 нет. Оба Tilda-загрузчика и обе локальные test-страницы используют собственные CSS/JS с `?v=2`. jsPDF закреплён на 4.2.1, V1 не изменяется.

У PVC-поворотных и поворотно-откидных секций добавлено `sections[].hingeSide: 'left' | 'right'`. Поле «Петли» скрыто у глухих и алюминиевых секций. Новые секции получают левую сторону; у старых секций без поля направление остаётся неизвестным: в описании «петли не указаны», в схеме знак вопроса вместо выдуманного направления. Равное перераспределение ширин сохраняет выбранные петли. Общая функция `windowSketch.drawOpening` рисует треугольник вершиной к петлям и отметки на стороне петель; SVG и PDF используют те же примитивы.

Смена `doorSide` переставляет реальные области окна и двери, их размерные линии и подписи. Для полного зеркального отражения выбранные `hingeSide` тоже переключаются слева/справа; интерфейс прямо сообщает это, и после зеркалирования петли можно уточнить вручную. Неизвестные петли не получают предполагаемую сторону. Все четыре размера, площадь и цена блока сохраняются.

В PricingConfig добавлен массив `pvcProfiles: [{ id, name, pricePerM2 }]`. Default ID — **exprof, veka, rehau**, совпадают с прежними ключами изделий; названия и ставки по умолчанию прежние. Адаптер преобразует старый `glazing` в массив в памяти с сохранением пользовательских ставок. `glazing` также остаётся производной картой ставок для прежних расчётных функций. Явно сохранённый пустой список не заменяется defaults автоматически.

Настройки позволяют переименовать профиль, изменить ставку, добавить и удалить профиль. Новые ID генерируются независимо от позиции в массиве. Индексы используются только для полей текущей формы. Обычный ввод не перерисовывает форму; добавление/удаление структурно обновляет её, сохраняя ещё не отправленные значения остальных полей.

Все PVC flow получают список из PricingConfig. Для существующего профиля действуют актуальные название и ставка, как раньше актуальные ставки настроек влияли на текущий расчёт. В изделии хранится `profileSnapshot: { id, name, pricePerM2 }`. Перед сохранением настроек/сбросом настройки резервируют параметры всех используемых профилей в текущем замере, включая старые изделия без snapshot и черновик. После удаления профиль остаётся доступен только уже использующему его изделию с сохранённой ставкой и названием; новые изделия его в списке не получают. Удалённый профиль помечен в редакторе, но эта служебная пометка не попадает в КП. Добавление snapshot само по себе не инвалидирует старую фиксированную цену; изменения стоимости по-прежнему требуют подтверждения согласно прежней логике.

Для `double`/`triple` в режиме PVC доступны `hasTopTransom` и `transomHeightMm`. Отсутствие флага в старом изделии означает выключенную фрамугу. При включении требуется `0 < transomHeightMm < height`; нижняя высота вычисляется автоматически. Неверное значение не исправляется молча: сохранение блокируется, некорректный эскиз не рисуется. Верхняя область цельная и глухая; вертикальные импосты и открывания ограничены нижней частью. Размерные линии показывают общие размеры и высоту фрамуги, КП содержит её высоту и конфигурацию с петлями. Площадь остаётся `width × height / 1e6`; фрамуга, петли и зеркалирование не добавляют цену или монтаж. Фрамуги не включены для блока, алюминия и остекления балкона.

Дополнительные проверки в `tests/`: `v2-hinges-math.cjs`, `v2-hinges-browser.cjs`, `v2-hinges-pdf.cjs`. Последняя проверка читает PDF, созданный браузерной, и использует `PDFJS_MODULE`. Проверены новые сценарии 1–13, legacy-направления/ставки/фиксированная цена, snapshots при удалении, ввод/caret, восстановление/копирование и PDF. Старые `v2-math`, `v2-browser`, `v2-pdf` остаются регрессионными тестами. Проверены рендеры PDF с 400/500 мм фрамугой и многостраничное КП на 22 изделия. Реальные мобильные устройства и опубликованная Tilda требуют проверки пользователем; локально используются Chrome и имитация Share API.

Для публикации после локальной проверки обновите три существующих V2 assets на GitHub и оба T123 загрузчиками с `?v=2`. README, test-loaders и тесты сохраняйте в репозитории проекта; production новых подключений не требует. Commit/push автоматически не выполняются.

## Виды замеров V2

Пять самостоятельных пунктов: «Пластиковое остекление», «Алюминиевое остекление», **«Остекление балкона»**, «Отделка окна», «Отделка балкона». Остекление и отделка балкона — разные сущности.

У ПВХ сохранены двустворчатое, трёхстворчатое окно и малый балконный блок, прежние профили/ламинация/фурнитура/отделки. У алюминия открывания «Глухая» и «Раздвижная». При явной смене материала несовместимое открывание сбрасывается в «Глухая»; цена от открываний не зависит.

Остекление балкона сначала запрашивает ПВХ/алюминий, затем форму: прямое (фасад), Г (фасад и боковая сторона слева/справа), П (левая, фасад, правая). Используются прежние ставки ПВХ/алюминия, коэффициенты ламинации/цвета. Неактивные плоскости сохраняются в замере, но не входят в стоимость.

Плоскости редактируются по одной через вкладки. У каждой ширина, высота, 1–8 секций с отдельным открыванием, автоматическое равное деление и ручные ширины. Несовпадение суммы ширин отмечается, но не блокирует цену: она считается по общей ширине плоскости, эскиз использует равные пропорции. Количество секций и положительные габариты валидируются.

«В пол» добавляет один горизонтальный импост. Высоты верхнего и нижнего ярусов должны быть положительными и в сумме совпадать с общей высотой; иначе сохранение блокируется. Нижний ярус глухой, повторяет вертикальное деление, заполняется стеклом или сэндвичем. Для отделки каждой плоскости используются её полные ширина/высота и прежние функции отделки, с проверкой глубины.

## Геометрия и цена

Малый балконный блок V2 хранит четыре размера. Площадь конструкции:

```text
(windowWidthMm × windowHeightMm + doorWidthMm × doorHeightMm) / 1_000_000
```

Для окна 1400 × 1500 и двери 700 × 2200 получается **3,64 м²**, а не 4,62. Эта площадь идёт в стоимость профиля и отображаемый монтаж. Отделка получает другой габарит: **2100 × 2200 мм**, то есть ширину окна + двери и высоту двери. Сами формулы отделки не изменены. В новом неполном блоке цена конструкции не подменяется ценой внешнего прямоугольника; нужно заполнить все четыре размера.

Остекление балкона: `totalAreaM2 = Σ(widthMm × heightMm) / 1_000_000`. В режиме «В пол» учитывается вся высота. Сэндвич занимает только нижнюю площадь выбранных плоскостей; `glassAreaM2 = totalAreaM2 − sandwichAreaM2`.

```text
basePrice = прежняя формула ПВХ с ламинацией или алюминия с цветом
sandwichAdjustment = sandwichAreaM2 × sandwichDiscountPerM2
installationDisplayPrice = totalAreaM2 × installationDisplayRatePerM2
displayedConstructionPrice = basePrice − sandwichAdjustment − installationDisplayPrice
constructionAndInstallationTotal = basePrice − sandwichAdjustment
```

Монтаж **не прибавляется** к старой цене. Пример: 3 м² × 18 000 = 54 000, из них конструкция 45 000 и монтаж 9 000. С односторонней ламинацией: 61 200 + 9 000 = прежние 70 200. Снижение за сэндвич — абсолютное, после коэффициентов, монтаж остаётся по полной площади. Четыре м² сэндвича дают снижение 4000 ₽. Клиент видит скорректированную конструкцию, без строки технической корректировки. Отделки и дополнительные работы считаются отдельно, скидки применяются по прежней логике.

Если настройки приводят к отрицательной стоимости конструкции после выделения монтажа/сэндвича, выдаётся ошибка с просьбой проверить ставки. Цена не повышается скрытно и не обрезается до нуля.

Новые defaults PricingConfig: `installationDisplayRatePerM2: 3000`, `sandwichDiscountPerM2: 1000`; `hardwareDefault: 'Стандартная'` сохранён. Все доступны в V2 settings. Пользовательские старые ставки не сбрасываются.

«СТИЗ» и «Работа с лесов» добавлены как быстрые названия дополнительных работ с **пустой ручной ценой**. Автоматических ставок или зарплатного прайса нет.

## State и совместимость

Ключи остались `remok.estimator.pricing.v1` и `remok.estimator.estimate.v1`, версия сохранённого замера — 1. Новые поля необязательны для старых замеров:

```js
// Новый малый блок
{ geometryVersion: 2, windowWidthMm, windowHeightMm,
  doorWidthMm, doorHeightMm, doorSide, sections }

// Самостоятельное остекление балкона, элемент items
{ mode: 'balcony-glazing', balconyGlazingMaterial: 'pvc',
  balconyGlazingShape: 'u', sidePosition: 'right', activePlaneId: 'facade',
  planes: [{ id: 'facade', widthMm, heightMm, sectionCount, sections,
    sectionWidthsAuto, heightMode: 'floor', upperHeightMm, lowerHeightMm,
    lowerFilling: 'sandwich', exterior, interior }], sandwichAdjustment }

// Внутренние данные клиента
{ contactPreference: 'phone', telegramUsername: '' }
```

Типы связи: `phone`, `whatsapp`, `telegram`, `max`. Telegram username необязателен и показывается в редакторе только для Telegram. Основной телефон хранится отдельно. В модель КП копируются только имя, телефон и адрес — внутренние предпочтения и username туда не попадают.

Legacy малый блок без четырёх размеров сохраняет прежний расчёт и условное изображение до редактирования. Открытие на редактирование создаёт черновик с незаполненными новыми размерами; исходная сохранённая позиция не меняется до сохранения. Отмена оставляет прежнюю цену. Неизвестная геометрия не выдумывается. Копирование/перезагрузка сохраняют новые поля, изменение цен обновляет производную корректировку и проверку фиксированной итоговой цены.

Совместимость направлена **из V1 в V2**. V1 не умеет рассчитывать новые виды изделий V2; из-за общих ключей не следует попеременно редактировать один V2-замер в старой и новой версиях. Сохранность V1 означает сохранность её файлов, а не поддержку новых данных старым кодом. Для изолированной проверки версий используйте разные профили браузера/origin. На одном origin V2-калькулятор и V2-настройки используют общие цены.

## SVG, PDF и печать

Расширена прежняя геометрическая модель `rect/line/text` в секции `v2-model` внутри JS. SVG и jsPDF используют одни координаты. Малый блок рисуется по реальным размерам с отдельными высотами и зеркальной дверью. Балконы показываются развёртками в порядке плоскостей; 3D нет. Сэндвич обозначается векторной штриховкой, раздвижные створки — стрелками. Не вводятся изображения, canvas или новые библиотеки.

PDF остаётся коммерческим предложением A4 с кириллицей, реквизитами, ценами и скидкой. Каждая плоскость имеет собственный блок и перенос страницы; три плоскости не ужимаются в миниатюру. Данные документа и заголовок отделены от renderer для будущего приложения к договору. Договор и печать организации не добавлены. Обычная браузерная печать и Web Share fallback сохранены.

## Шаг 5. Выпускать дальнейшие обновления

Измените соответствующие внешние файлы → опубликуйте их новую версию → при необходимости увеличьте `?v=1` до `?v=2` → перепубликуйте Tilda, только если изменился загрузчик или URL/version.

При изменении цен по умолчанию или общей логики конфигурации обновляйте оба JS-файла согласованно: каждый содержит свой экземпляр исходной конфигурации и работы с хранилищем. Изменения пользовательских цен по-прежнему выполняются на странице настроек и публикации не требуют. CDN может кешировать содержимое отдельно от браузера: query-параметр не заменяет обновление/очистку кеша самого CDN; для неизменяемых URL используйте новый опубликованный путь/ревизию.

## PDF и внешние ресурсы

Единственная сторонняя сетевая зависимость калькулятора:

`https://cdn.jsdelivr.net/npm/jspdf@4.2.1/dist/jspdf.umd.min.js`

Она подключена отдельным `script defer` **перед** `remok-estimator.js`. Не заменяйте `defer` на `async`: порядок загрузки важен для готовности PDF. Исходник jsPDF не включён в собственный внешний JS. Странице настроек PDF-библиотека не нужна.

Кириллический шрифт Remok Sans (сокращённый Noto Sans, SIL OFL 1.1) встроен как данные в секцию `font-data` файла `remok-estimator.js`; лицензия сохранена там же. Поэтому публиковать четвёртый файл шрифта не нужно. Бизнес-код и PDF-модуль разбиты на именованные секции, не минифицированы. `window.Remok` — сохранённое пространство имён приложения; `window.jspdf` создаёт библиотека.

PDF остаётся текстовым A4 и формируется из данных сметы. «Поделиться КП», «Скачать КП», резервная ссылка, отмена отправки и «Печать» сохранены. Web Share API требует HTTPS и поддержки передачи файлов; доступность приложений определяет телефон. Если CDN jsPDF недоступен, калькулятор продолжает рассчитывать, а PDF-действия показывают прежнее сообщение об ошибке и предлагают печать. После восстановления сети обновите страницу.

## Инициализация и стили

Каждый JS-файл имеет IIFE и отдельный флаг инициализации на `document`. До готовности DOM он ждёт `DOMContentLoaded`; при более поздней вставке корневого блока ждёт его через `MutationObserver`. Повторная загрузка того же JS не запускает приложение ещё раз и не добавляет повторные обработчики. Наблюдатель отключается после запуска.

Обе страницы сохраняют безопасный корневой контейнер `#remok-estimator`; форма настроек внутри него имеет прежний `#remok-settings`. Все селекторы CSS ограничены корневым контейнером, A4 задаётся именованным `@page remok-estimate`. Внешние блоки Tilda не скрываются даже при печати: для печати только сметы используйте страницу без дополнительных шапок/подвалов Tilda.

## Сохранение данных

Ключи не изменены:

- `remok.estimator.pricing.v1` — цены;
- `remok.estimator.estimate.v1` — текущий замер.

Скрипт с CDN выполняется в контексте страницы Tilda и использует хранилище её домена, а не домена CDN. `/calc` и `/calc-settings` должны быть на одном origin: одинаковые HTTPS, домен и порт. Переезд файлов не очищает хранилище. Старые цены объединяются с defaults без сброса пользовательских значений. Изменения цен видны после возврата к калькулятору и в другой вкладке через `storage`.

## Типы ПВХ-изделий и данные

Стартовый пункт «Пластиковое остекление» сохранён. В редакторе выбирается тип: двустворчатое, трёхстворчатое окно или малый балконный блок. Дальше используются прежние `width`/`height` в миллиметрах и прежние расчёты. Промежуточный вопрос про отделку балкона убран: после сохранения доступны добавление изделия, отдельной отделки балкона и переход к смете.

Пример новых полей изделия (остальные поля остаются прежними):

```js
{
  productType: 'triple', // double | triple | balcony_small
  width: 2100, height: 1450,
  sections: [
    { widthMm: 700, openingType: 'fixed' },
    { widthMm: 700, openingType: 'tilt_turn' },
    { widthMm: 700, openingType: 'turn' }
  ],
  sectionWidthsAuto: true,
  doorSide: 'right', // left | right, для balcony_small
  hardware: 'Стандартная'
}
```

Пока ширины автоматические, изменение общей ширины перераспределяет секции поровну (остаток — последней секции). Ручной ввод отключает это поведение; кнопка «Разделить ширину поровну» включает его снова, сохраняя открывания. Несовпадение суммы или незаполненные детальные ширины не блокируют цену. Корректные ширины определяют пропорции схемы; иначе рисуются равные секции с пояснением. У балконного блока индекс 0 всегда обозначает окно, индекс 1 — дверь, независимо от стороны двери.

`PricingConfig.hardwareDefault` — текст, по умолчанию «Стандартная». Страница настроек сохраняет его как строку; старые числовые ставки объединяются с defaults как раньше. Новые изделия получают копию этого текста, которую можно изменить индивидуально. Фурнитура, секции, тип и сторона двери не добавляют цену. Площадь, ставки, область применения ламинации и логика скидок не изменены.

Ключи localStorage и `version: 1` сохранены; структура расширена необязательными полями. Для legacy без `productType` тип и конфигурация считаются неизвестными: никаких предполагаемых створок или эскиза. Пустая/отсутствующая фурнитура отображается через текущий `hardwareDefault`; если его нет в старой конфигурации — «Стандартная». Старый шаг `balcony-question` переводится на экран сметы. Автосохранение, копирование и возврат сохраняют новые поля.

## Общий эскиз и коммерческое предложение

В `remok-estimator.js` добавлена секция `window-sketch` (`Remok.windowSketch`). `geometry(product, options)` возвращает размерную модель с примитивами `rect`, `line`, `text`. `renderWindowSketch` превращает её в SVG для редактора, карточек и read-only сметы, а `drawPdf` рисует ту же модель средствами jsPDF. Bitmap, canvas и дополнительная библиотека не нужны. Общие пропорции ограничены для читаемости. Высота оконной части балконного блока условная (65% высоты схемы) и явно подписана как не являющаяся замером; в цене используются прежние общие размеры.

Для нового типа позже добавьте запись в `windowSketch.types` и при необходимости вариант геометрии. Параметры секций и характеристики уже отделены от расчётных функций. Для новых размерных линий расширяйте общую геометрию: SVG и PDF используют одни примитивы.

Экран остаётся «Итоговая смета», без редактируемых полей. Клиентские позиции ПВХ называются «Профиль …». Кнопки «Поделиться КП» и «Скачать КП» создают **коммерческое предложение** A4: дата формирования, клиент/объект, изделия с характеристиками и векторными схемами, отдельная отделка балкона, работы, скидка, итог и реквизиты. Номер КП пока не вводится. Кириллица и прежний Share API fallback сохранены.

`estimatePdfData()` создаёт снимок данных с `document: { mode, title, date }`, `company`, изделиями, работами и итогами. PDF renderer принимает заголовок из этого описания, а не из UI. Эти данные пригодны для будущего приложения к договору; генерации договора в PATCH нет. Company details находятся в `Remok.company` секции config; реквизиты, ОГРН, телефон и email сверены с `v4/index.html`. Банковские данные не добавлены.

## Проверки PATCH и ограничения

Проверены в локальном Chrome с production-загрузчиками и подменой CDN на локальные файлы: старые сценарии ПВХ/ламинации, алюминий, обе отделки, балкон, работы, скидки, настройки, телефон, ввод чисел без замены активного input; три типа, секции, открывания, зеркальная дверь, reload/duplicate/возврат и read-only документ. PDF проверяется извлечением текста и границ, отрисовкой страниц, многостраничными заказами, кириллицей и длинными описаниями. Share API, отмена, отказ, отсутствие поддержки и iOS fallback проверяются имитацией браузерных API.

Реальные Safari/iPhone и Android не заменяются эмуляцией: окончательную отправку в приложения нужно проверить на устройствах после публикации. Развёртывание в Tilda/GitHub здесь не выполняется. SVG — схема, а не производственный CAD; произвольное количество секций и дополнительная высота оконной части не поддерживаются.

Production assets по-прежнему только три: `remok-estimator.js`, `remok-settings.js`, `remok-estimator.css`. Все три нужно загрузить повторно. Нового внешнего файла нет, порядок script tags не меняется. Оба T123 обновляются короткими загрузчиками с `?v=2`; локальные test-страницы тоже обновлены. Исходная автономная версия вне `tilda/` этим PATCH не изменяется. Не пересобирайте production JS из старых `../js/`: новая логика находится в именованных секциях production assets.
